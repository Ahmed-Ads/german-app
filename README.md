# 🇩🇪 تطبيق تعلّم الألمانية للمتحدثين بالعربية · Deutsch lernen

تطبيق ويب تقدمي (PWA) متكامل لتعليم اللغة الألمانية، يضم 1,160 مفردة مفحوصة آلياً وموزعة على 30 قسماً، مع صيغ الجمع، التكرار المتباعد الذكي (SRS)، أنماط استماع وبطاقات 3D، وتفضيل تلقائي لأصوات النطق الألمانية الرجالية، ويعمل بكفاءة تامة دون الحاجة إلى اتصال بالإنترنت.

## 🚀 1. التشغيل المحلي (على حاسوبك)

- **الطريقة الموصى بها:** اضغط مرتين على `Run_App.bat` لتشغيل خادم محلي آمن مرتبط بالعنوان `127.0.0.1:8000` وفتح التطبيق تلقائياً في المتصفح (أو نفّذ `python -m http.server 8000`). فتح ملف `index.html` مباشرة عبر بروتوكول `file://` لا يدعم Service Worker ولا يوفر إمكانيات التخزين المؤقت للعمل دون اتصال، كما يمتلك مساحة تخزين محلية منفصلة.

## 🌐 2. النشر والتوافق مع Cloudflare Pages (استضافة مجانية للمستودعات الخاصة)

تم اختيار **Cloudflare Pages** لاستضافة التطبيق مجاناً مع إبقاء الكود المصدري داخل **مستودع خاص (Private Repository)** على GitHub، لأن GitHub Pages المجاني يتطلب مستودعاً عاماً.

### إعدادات البناء المعتمدة (Build Settings):
عند ربط المستودع في لوحة تحكم Cloudflare Dashboard (**Workers & Pages** > **Create application** > **Pages** > **Connect to Git**)، اضبط الإعدادات التالية بدقة:
- **Framework preset:** `None` (تطبيق بدون إطار عمل).
- **Build command:**
  ```bash
  node scripts/build_site.js
  ```
- **Build output directory:**
  ```text
  site
  ```
- **Root directory:** `/` (اتركه فارغاً، ليعتمد جذر المستودع).
- **إصدار Node.js (اختياري/موصى به):** في **Settings** > **Builds & deployments** > **Environment variables**، يمكن إضافة المتغير `NODE_VERSION` بالقيمة `20`.

### سلوك التوجيه والتوافق الهندسي (Routing & SW Compatibility):
- **التحويل التلقائي للروابط النظيفة:** تُجري Cloudflare Pages تحويلاً دائماً (HTTP 308) لأي طلب للمسار `/index.html` إلى الجذر التوجيهي النظيف `/` (Clean URLs).
- **معالجة استجابات التنقل (Navigation Responses):** تنص مواصفة Fetch و Service Worker على حظر الاستجابة لطلبات التنقل (Navigation) باستجابة تحمل راية التحويل `response.redirected === true` لتجنب أخطاء المتصفح وفشل التشغيل أوفلاين. لذا تم ضبط التطبيق هندسياً كالتالي:
  1. ضبط `start_url: "./"` داخل `manifest.json`.
  2. تضمين المسار الأساسي `'./'` في التخزين المسبق الحرج `CRITICAL_ASSETS` بملف `sw.js` (بدلاً من `'./index.html'`).
  3. إعادة بناء أي استجابة شبكية محولة لتكون استجابة نظيفة (`cleanRedirectedResponse`) قبل التخزين المؤقت عبر `cache.put` وقبل الإرجاع للمتصفح.
  4. اعتراض طلبات التنقل التي تنتهي بـ `/index.html` وتقديم استجابة الجذر النظيفة المخزنة فورياً للعمل دون اتصال بكفاءة تامة.
- **ملف الترويسات (`_headers`):** يتضمن مجلد الإنتاج `site/` ملف `_headers` لضبط `Cache-Control: no-cache` لكل من `/sw.js` و `/manifest.json` لضمان عدم احتفاظ خوادم الحافة (CDN) بنسخ قديمة منهما وسرعة وصول التحديثات للمستخدمين.

### الفحوصات اليدوية على الرابط الحقيقي بعد النشر (Manual Verification on Real URL):
نظراً لأن بيئات الفحص الآلي (CI) تعمل محلياً ومحاكاتياً، يجب إجراء الفحوصات الثلاثة التالية يدوياً على الرابط الفعلي المنشور (`https://german-app-ads.pages.dev`) للتأكد التام:
1. **الفحص الأول (أونلاين - Online):** افتح الرابط المباشر في المتصفح، وتأكد من تحميل كافة الأقسام (30 قسماً) وتفعيل كاش Service Worker v13 دون أي أخطاء في Console.
2. **الفحص الثاني (أوفلاين - Offline):** افصل الاتصال بالإنترنت (أو اختر Offline من تبويب Network في DevTools)، ثم أعد تحميل الصفحة في المسارين: `/` وكذلك `/index.html`، وتأكد من ظهور الأقسام والتفاعل السليم.
3. **الفحص الثالث (التشغيل من أيقونة PWA المثبتة أوفلاين - Launch from Installed Icon Offline):** ثبّت التطبيق كـ PWA على الهاتف أو الحاسوب، وافصل الإنترنت تماماً، ثم شغّل التطبيق من الأيقونة المثبتة على سطح المكتب أو الشاشة الرئيسية، وتأكد من فتح التطبيق وظهور الـ 30 قسماً دون انقطاع، مع خلو Console من أي أخطاء.
*(تنبيه أمان وموثوقية: هذه الفحوصات الثلاثة على النطاق الحقيقي تُجرى يدوياً فقط، ولا ندعي التحقق منها على الخادم الحقيقي آلياً).*

## 📋 3. روتين إصدار التحديثات (Release Routine)

عند إجراء أي تحديث أو تحسين مستقبلي، اتبع الخطوات التالية بالترتيب:

1. **التحقق من كافة البوابات (Verify):**
   ```bash
   npm run test:all
   ```
   أو قم بتشغيل فحص ويندوز الشامل عبر النقر المزدوج على `Run_Windows_Checks.bat`.
2. **ترقية إصدار الكاش (Bump CACHE_NAME):**
   - افتح ملف `sw.js` وقم بزيادة رقم الإصدار في `CACHE_NAME` (مثلاً من `deutsch-lernen-v14` إلى `deutsch-lernen-v15`).
   - اختبار `tests/sw_static_check.test.js` يتحقق من اسم الكاش تلقائياً.
   - إن غيّرت أي ملف مخزّن مؤقتاً (مثل `sync/*.js` أو الخطوط أو الأيقونات) دون ترقية `CACHE_NAME` سيفشل اختبار `tests/sw_cache_version.test.js` ويخبرك بالخطوة المطلوبة. بعد الترقية شغّل:
     ```bash
     npm run update:sw-baseline
     ```
3. **الالتزام (Commit):**
   ```bash
   git add .
   git commit -m "feat: وصف التحديث الجديد"
   ```
4. **الدفع (Push):**
   ```bash
   git push origin main
   ```
   ستقوم Cloudflare Pages تلقائياً بسحب التحديث، وبناء المجلد `site/` ونشر النسخة الجديدة في ثوانٍ.

## 🛠️ 4. أين تعدّل ماذا؟ (Where to Change What)

- **تعديل المفردات الألمانية (Vocabulary):**
  - **تنبيه صارم (Rule R1):** لا تعدل الكلمات اعتباطياً. أي تعديل في المفردات داخل `index.html` يتطلب توثيقاً بمصادر لغوية معتمدة (Duden/DWDS)، وتحديثاً متعمداً لقاعدة المرجع عبر:
    ```bash
    python verify_vocab.py --update-baseline --reason "سبب التعديل" --source "المصدر اللغوي" --ids "المعرف"
    ```
    سيتم تسجيل الهاش الجديد تلقائياً في `CHANGELOG_VOCAB.md`.
- **تعديل التصميم والألوان والأنماط (CSS):**
  - يتم التعديل داخل قسم `<style>` في `index.html`. لا يتطلب تغيير الكاش لأن أنماط CSS تستخدم استراتيجية *Stale-While-Revalidate* وتتحدث فورياً في الخلفية.
- **تعديل منطق التطبيق والواجهة (JavaScript):**
  - يتم داخل قسم `<script>` في `index.html`. بعد التعديل، يجب ترقية `CACHE_NAME` في `sw.js` ليحصل المستخدمون على التحديث.
- **تعديل وترقية Service Worker (الكاش والعمل Offline):**
  - يتم التعديل في `sw.js`. تذكر تغيير `CACHE_NAME` عند إضافة ملفات جديدة للأصول الثابتة.
- **تعديل تفضيلات الصوت (TTS Voices):**
  - يتم ضبط ترتيب الأصوات وقائمة الأسماء الرجالية المدعومة داخل كائن منطق الصوت في `index.html`، وتوثيق أي اسم جديد بمصدر رسمي في `docs/tts_voices.md`.

إذا أظهر التطبيق رسالة تفيد بعدم العثور على صوت ألماني رجالي على جهازك، يمكنك تثبيت حزمة صوتية إضافية عبر إعدادات النظام:

## ☁️ 7. المزامنة السحابية الاختيارية وحفظ التقدم عبر الأجهزة (Cross-Device Cloud Sync)

يتضمن التطبيق ميزة **مزامنة سحابية اختيارية تماماً** تتيح تسجيل الدخول بحساب Google لمزامنة التقدم بين الهاتف والحاسوب والأجهزة اللوحية بسلاسة تامة، مع بقاء التطبيق يعمل بشكل مستقل وبلا إنترنت (Offline-First) ودون أي تغيير لمن لا يرغب في إنشاء حساب. التطبيق مهيأ للربط بمشروع Firebase الرسمي (`german-app-ads`) والموقع المنشور (`https://german-app-ads.pages.dev`).

### 💰 ضمان المجانية الكاملة وحسابات الاستهلاك (Free Tier Quota Math)
تعتمد المزامنة على باقة **Firebase Spark (المجانية بالكامل)**.
- **لا تتطلب إدخال أي بطاقة ائتمان** ولا يمكن أن تفرض أي رسوم مالية على الإطلاق (Hard-Capped Quota).
- **حدود الباقة المجانية اليومية:**
  - سعة التخزين: **1 جيجابايت** (1 GiB).
  - عمليات القراءة: **50,000 عملية قراءة يومياً** (50,000 reads/day).
  - عمليات الكتابة: **20,000 عملية كتابة يومياً** (20,000 writes/day).
  - عمليات الحذف: **20,000 عملية حذف يومياً** (20,000 deletes/day).
- **حساب الاستهلاك الفعلي للمستخدم الشخصي:**
  - يتم تخزين كل تقدم المستخدم في **وثيقة واحدة فقط** لكل مستخدم: `users/{uid}`.
  - حجم الوثيقة الكاملة بجميع الأقسام الـ 30 والإحصائيات والكلمات المميزة يتراوح بين **35 و 50 كيلوبايت فقط** (أقل من 5% من الحد الأقصى المسموح للوثيقة الواحدة وهو 1 ميجابايت).
  - يتم تجميع وحفظ التعديلات آلياً بتقنية Debounce (بفاصل 30 ثانية أو عند مغادرة الصفحة أو إغلاق التطبيق)، ما يعادل نحو **60 إلى 120 عملية كتابة يومياً** أثناء الاستخدام المكثف، أي **أقل من 0.6% من الحصة اليومية المجانية**!
  - القراءة تتم فقط عند فتح التطبيق لأول مرة أو تسجيل الدخول، بمعدل نحو **5 إلى 15 عملية قراءة يومياً** (أقل من 0.03% من الحصة المجانية).

> ⚠️ **تنبيه صارم:** إذا طُلب منك في أي خطوة أثناء إعداد Firebase إدخال بيانات بطاقة بنكية أو الترقية لخطة Blaze المدفوعة، **توقف فوراً ولا تُدخل بطاقتك**؛ فباقة Spark مجانية تماماً للمستويات الشخصية ولا تتطلب أي بطاقة.

### 📋 خطوات الإعداد اليدوي خطوة بخطوة (10-Step Setup Checklist)

اتبع هذه الخطوات البسيطة لإعداد قاعدة بياناتك السحابية الخاصة مجاناً:

1. **نشر التطبيق على Cloudflare Pages أولاً:**
   - انشر التطبيق للحصول على رابط النطاق الإنتاجي الرسمي (`https://german-app-ads.pages.dev`).
2. **إنشاء مشروع Firebase جديد:**
   - ادخل إلى [Firebase Console](https://console.firebase.google.com/)، واضغط **Add project**.
   - اختر اسماً للمشروع (مثل `german-app-ads`).
   - اختر خطة **Spark (Free)** وتأكد من عدم تفعيل خطة مدفوعة.
3. **تفعيل تسجيل الدخول عبر Google:**
   - من القائمة الجانبية، اختر **Build** ثم **Authentication**.
   - اضغط **Get started**، ومن تبويب **Sign-in method** اختر **Google** وقم بتفعيله (Enable).
   - حدد بريد الدعم الخاص بك ثم اضغط **Save**.
4. **إضافة النطاقات المصرح لها (Authorized Domains):**
   - داخل صفحة **Authentication**، انتقل إلى تبويب **Settings** ثم قسم **Authorized domains**.
   - تأكد من وجود `localhost`، واضغط **Add domain** وأضف نطاقك على Cloudflare Pages (`german-app-ads.pages.dev`).
5. **إنشاء قاعدة بيانات Cloud Firestore:**
   - من القائمة الجانبية، اختر **Build** ثم **Firestore Database**.
   - اضغط **Create database**، واختر الوضع الإنتاجي **Start in production mode**.
   - اختر أقرب موقع جغرافي لك (مثل `europe-west3` فرانكفورت أو `europe-west1` بلجيكا) واضغط **Enable**.
6. **تطبيق قواعد الأمان وتقييد الحساب (Firestore Security Rules & Single-Owner Hardening):**
   - داخل صفحة **Firestore Database**، انتقل إلى تبويب **Rules**.
   - انسخ محتوى الملف المرفق في المشروع [firestore.rules](./firestore.rules).
   - ⚠️ **هام جداً - تقييد الحساب لمالك التطبيق فقط:**
     يحتوي ملف القواعد في المستودع على قيمة عنصر نائب نصية: `'ALLOWED_UID_PLACEHOLDER'`. طالما بقيت هذه القيمة دون تعديل، فإن الوصول السحابي مرفوض تلقائياً (Fail-Closed) بموجب القواعد لحماية بياناتك. يجب عليك استبدال هذا النص يدوياً داخل محرر Firebase Console فقط بمعرّف حسابك الحقيقي (Firebase Auth UID) الخاص بك (يمكنك نسخه من صفحة Authentication بعد تسجيل دخولك الأول). **لا تقم أبداً برفع أو تضمين معرّف حسابك الحقيقي في كود المستودع العام**.
   - **الحدود الهيكلية وحدود لغة القواعد:**
     تفرض القواعد قيوداً واقعية مشتقة من بيانات التطبيق (30 قسماً و 1160 كلمة):
     - `progress.size() <= 35` (أقسام التطبيق مع هامش أمان).
     - `stats.size() <= 10` (حقول الإحصائيات المعروفة).
     - `starred.size() <= 1200` (قائمة المفضلة).
     - `srs.size() <= 1200` (نظام التكرار المتباعد).
     - `dailyGoal.target` محصور بين 5 و 200 كلمة حصراً.
     - طول السلاسل النصية للتواريخ `updatedAt.size() <= 40`.
     - اشتراط وتحديد الحقول الثمانية الإلزامية عبر `keys().hasAll(...)` و `keys().hasOnly(...)`.
     - *ملاحظة توثيقية شفافة حول حدود لغة Firestore Rules:* لا تدعم لغة قواعد Firestore التكرار الحلقي (Iteration) الديناميكي على مفاتيح الخرائط المتداخلة؛ لذلك يتم ضبط الأمان بتحديد حجم الخرائط والمصفوفات، وحصر المفاتيح العلوية، والتحقق الصارم من الأنواع والنطاقات العددية.
   - اضغط **Publish** لنشر القواعد.
7. **تقييد مفتاح الواجهة البرمجية (Restrict Web API Key):**
   - في [Google Cloud Console Credentials](https://console.cloud.google.com/apis/credentials)، افتح المفتاح المسمى `Browser key (auto created by Firebase)`.
   - تحت قسم **Application restrictions**، اختر **Web sites** وأضف نطاقاتك المسموح بها فقط (`https://german-app-ads.pages.dev/*` و `http://localhost:*`).
8. **إعدادات `firebase-config.js`:**
   - ملف [firebase-config.js](./firebase-config.js) في المستودع مضبوط مسبقاً لمشروعك `german-app-ads`.
9. **اختبار المزامنة عبر جهازين:**
   - افتح التطبيق على حاسوبك، وسجل الدخول بحساب Google وأجب عن بعض الأسئلة واضغط "حفظ سحابي".
   - افتح التطبيق على هاتفك وسجل الدخول بنفس الحساب، وستجد تقدمك وإحصائياتك ومستويات إتقانك قد ظهرت تلقائياً!
10. **مراقبة الاستهلاك الشهري في الكونسول:**
    - يمكنك في أي وقت الدخول إلى **Usage and billing** داخل Firebase Console للاطمئنان على بقاء استهلاكك ضمن الصفر دولار ونسب الاستخدام المتناهية الصغر.

### 🛡️ أمان مفاتيح الويب (Why Web API Keys are Public by Design)
في تطبيقات الويب أحادية الصفحة (SPAs) وتطبيقات الويب التقدمية (PWAs)، تُعتبر مفاتيح Firebase Web API مفاتيح تعريفية للمشروع (Identifiers) وليست أسراراً مشفرة. وهي موجودة في كود المتصفح لدى ملايين التطبيقات العالمية.
- **تنبيه البريد الإلكتروني الآلي من Google:** قد ترسل Google رسالة تنبيه آلية عبر البريد الإلكتروني تفيد باكتشاف مفتاح API في كود عام. هذا التنبيه آلي ومعتاد لمفاتيح الويب العامة ولا يمثل خطراً طالما أنك قيدت المفتاح بنطاقك وطبقت قواعد Firestore.
- **أين يكمن الأمان الحقيقي؟**
  1. **قواعد الأمان (Firestore Security Rules):** هي خط الدفاع الصارم؛ حيث يرفض خادم Google أي طلب قراءة أو كتابة لا يحمل توقيع المستخدم الصالح المحدد في `isOwner(userId)`، وتظل القواعد الافتراضية مغلقة تماماً ما دامت تحتوي على `'ALLOWED_UID_PLACEHOLDER'`.
  2. **تقييد النطاقات (HTTP Referrer Restriction):** يمنع استخدام المفتاح من خارج نطاق موقعك المعتمد.

### 📲 مسار الدخول البديل وحدود iOS Safari (Fallback Sign-In & iOS Limits)
- يدعم التطبيق مسار دخول بديل: في حال فشل النافذة المنبثقة (`signInWithPopup`) بسبب حظر النوافذ من قبل المتصفح (`auth/popup-blocked`) أو عدم دعمها في البيئة الحالية (`auth/operation-not-supported-in-this-environment` كما في تطبيقات PWA المثبتة على الشاشة الرئيسية)، ينتقل التطبيق تلقائياً إلى تسجيل الدخول عبر التحويل (`signInWithRedirect`).
- إذا قام المستخدم بإغلاق النافذة المنبثقة بنفسه (`auth/popup-closed-by-user`)، يُعد ذلك إلغاءً لطلب تسجيل الدخول وتظهر رسالة "تم إلغاء طلب تسجيل الدخول." دون التحويل التلقائي.
- **تنبيه شفاف بخصوص بيئة iOS / Safari:** مسار التحويل هذا لم يتم التحقق منه على هاتف آيفون فعلي أو جهاز iOS حقيقي. كما أن إعداد Cloudflare Pages بنطاق مخصص يختلف عن نطاق `*.firebaseapp.com` قد يتأثر بسياسة منع التتبع الذكي في سفاري (Apple Safari ITP)، والتي قد تحظر ملفات تعريف الارتباط للطرف الثالث (Third-party Cookies) أثناء التحويل. لا ندعي نهائياً ضمان عمل المزامنة على أجهزة iOS دون اختبار مباشر على أجهزة فعلية.

### 💾 تنزيل النسخة الاحتياطية الوقائية والدمج الأولي (First-Merge Backup Rule)
- **قاعدة الدمج الأول:** تُطلب النسخة الاحتياطية الوقائية تلقائياً وتُنزَّل فقط عند **الدمج الأولي** للمستخدم على هذا الجهاز (يتم تعيين علامة `deutsch_sync_first_merge_done_v1` في `localStorage` بعد أول دمج ناجح). عند عمليات الإطلاق اللاحقة واستئناف الجلسة المسجلة، لا يتم تنزيل نسخ احتياطية متكررة تجنباً لإغراق مجلد التنزيلات.
- **حدود المتصفح:** لا تتيح واجهات برمجة المتصفح القياسية (Browser APIs) وسيلة لمعرفة ما إذا كان المتصفح أو المستخدم قد حظر تنزيل الملف بعد النقر على الرابط (`a.click()`) دون إلقاء خطأ متزامن. لذلك يُسجل النظام إشعاراً للمستخدم بأن العملية هي "طلب تنزيل نسخة احتياطية" ويوجهه للتحقق من مجلد التنزيلات.
- لا تظهر رسالة التأكيد `confirm()` للمتابعة بدون نسخة احتياطية إلا في حال رمي استثناء صريح (مثل رفض الصلاحيات أو بيئة تمنع إنشاء الروابط والتنزيل التلقائي).

### 🔄 القراءة ثم الدمج ثم الكتابة وإعادة المحاولة المنضبطة (Read-Merge-Write on Save & Bounded Retry)
- **منع الكتابة السحابية العمياء:** عند حفظ التقدم السحابي المؤجل أو عند مغادرة الصفحة (`flushSave`)، لا يقوم `SyncManager` بالكتابة العمياء فوق المستند السحابي. بل يقوم بتحميل المستند السحابي أولاً، والتحقق من صحته عبر `validateCloudDocument`، ودمجه حتمياً مع البيانات المحلية عبر `mergeFullUserData`، وتحديث البيانات المحلية في الذاكرة دون إعادة تصيير الشاشة أثناء التمارين، ثم كتابة الناتج المدمج. هذا يمنع مسح تقدم أي جهاز آخر قيد التشغيل في نفس الوقت.
- **سياسة إعادة المحاولة المنضبطة (Bounded Retry Policy):**
  - **الأخطاء المؤقتة (Transient Errors):** مثل انقطاع الشبكة اللحظي أو خطأ 503، تتم إعادة المحاولة بحد أقصى 3 مرات مع تباعد زمني متزايد (30 ثانية، ثم دقيقتان، ثم 10 دقائق)، ثم يتوقف التطبيق عن إعادة المحاولة التلقائية لتفادي استهلاك الحصص سدى، وتظل علامة `pendingChanges = true` في حالة `ERROR`.
  - **الأخطاء غير المؤقتة (Non-transient Errors):** مثل عدم صلاحية المستند السحابي أو رفض الصلاحيات (`permission-denied`)، لا تتم أي إعادة محاولة تلقائية إطلاقاً (0 retries)، وتنتظر حدوث تغيير محلي جديد أو عودة الاتصال.
  - **حالة انقطاع الاتصال (Offline):** لا يتم تشغيل مؤقتات استطلاع دورية، بل ينتظر التطبيق حدث عودة الاتصال (`online`) أو استعادة الواجهة (`visibilitychange`).
  - **تزامن التعديلات أثناء الحفظ (In-Flight Change Safety):** يتم تتبع التعديلات عبر عداد ترتيبي (`_changeSeq`). فإذا أجرى المستخدم تعديلاً جديداً أثناء وجود طلب حفظ قيد التنفيذ، تظل علامة `pendingChanges = true` بعد اكتمال الحفظ الأول ويُجدول حفظ جديد لتحديث السحابة بالحالة الأحدث.

### 🔄 تصفير البيانات وسلوك المزامنة (Progress Reset Behaviour)
- عند تصفير كافة البيانات عبر زر "تصفير كل التقدم"، يتم مسح كافة حقول التقدم والإحصائيات وسجلات SRS، بالإضافة إلى حذف طابع الهدف اليومي (`deutsch_daily_goal_updated_at_v1`) ليعود إلى القيمة الافتراضية دون ترك طابع زمني قديم يتغلب على أجهزة أخرى. وتبقى علامة الدمج الأول (`deutsch_sync_first_merge_done_v1`) محفوظة.
- **إذا كان المستخدم مسجلاً ومزامناً:** يتم **حذف النسخة السحابية أولاً** (`deleteCloudData`). وفقط في حال نجاح الحذف السحابي، يتم مسح البيانات المحلية. أما إذا تعذر الحذف السحابي (مثل انقطاع الإنترنت)، **فلا يتم مسح البيانات المحلية** لحمايتها من الضياع أو استرجاع بيانات قديمة، ويظهر للمستخدم تنبيه صادق يوضح سبب عدم التصفير.
- **إذا كان غير مسجل:** تنبه رسالة التأكيد المستخدم إلى أنه في حال وجود نسخة سحابية على جهاز آخر، فقد تعود البيانات عند تسجيل الدخول والمزامنة مجدداً.

### ⌨️ اختصارات لوحة المفاتيح الآمنة (Safe Desktop Keyboard Shortcuts)
- تم نقل معالج الاختصارات إلى دالة محددة ومفحوصة `handleGlobalKeydown`.
- لا تعترض الاختصارات المتصفح عند الضغط على مفاتيح التعديل (`Ctrl`، `Meta/Cmd`، `Alt`)، أو أثناء تكوين الحروف عبر لوحات الإدخال (IME Composing)، أو عند التركيز على أي عنصر تفاعلي أو حقل إدخال (`input`، `textarea`، `select`، `button`، `a`، `summary`، `contenteditable`، `[role="button"]`).

### ⚖️ خاصية ثبات عدم التراجع (Monotonicity) ونظام التكرار المتباعد (SRS)
- تنطبق خاصية عدم التراجع الرياضية (Monotonicity) بدقة تامة على: عدادات الإتقان (`counts`)، المستويات المفتوحة (`unlocked`)، والإحصائيات التراكمية الكلية (`totalAnswered`، `totalCorrect`، `longest`).
- أما في نظام التكرار المتباعد الذكي (SRS)، فإن السجل صاحب تاريخ المراجعة الأحدث (`lastDate`) هو الذي يسود دائماً عند الدمج؛ حتى لو كان رقم الصندوق (`box`) فيه أقل. هذا السلوك مقصود ومنطقي: فإذا راجع المستخدم كلمة في وقت لاحق على أحد الجهازين وأخطأ فيها، فإن الصندوق ينخفض تلقائياً ومشروعاً لضمان تكرار الكلمة وتثبيتها.

### ⚡ التحميل الكسول لحزمة المزامنة (Lazy-Loading Firebase Bundle & Offline Resilience)
- **توفير الحجم وسرعة الإقلاع:** تزن حزمة Firebase المصغرة قرابة 611 كيلوبايت. لحماية تجربة مستخدمي التطبيق غير المهيأ للمزامنة، تم إلغاء التحميل المسبق للحزمة عند فتح التطبيق، وإلغاء تخزينها المسبق في Service Worker (`OPTIONAL_ASSETS`). هذا خفّض حجم الكاش المسبق بنسبة **52%** (من 1.17 ميجابايت إلى ~560 كيلوبايت فقط).
- **آلية التحميل:** لا يتم جلب الحزمة أو حقنها في الصفحة إطلاقاً طالما أن ملف `firebase-config.js` يحتوي على بيانات تجريبية (Placeholders). ويتم جلبها فقط عند قيام المستخدم بتهيئة المزامنة وطلب تسجيل الدخول أو فتح لوحة المزامنة.
- **المرونة أوفلاين:** في حال عدم توفر اتصال بالإنترنت عند طلب المزامنة لأول مرة، يُظهر التطبيق رسالة واضحة للمستخدم دون تجميد الواجهة، مع استمرار التطبيق بكامل وظائفه التعليمية (1,160 كلمة، التدريبات، الصوت، SRS) أوفلاين بالكامل وبكفاءة عالية.

### 🧭 التنقل وتكامل زر الرجوع (Navigation History & Back Button Integration)
- **دعم زر الرجوع في أندرويد وإيماءات السحب في iOS:** تم دمج التنقل مع واجهة المتصفح (`history.pushState` و `history.replaceState` وحدث `popstate`) بحيث يؤدي الضغط على زر الرجوع أو سحب الشاشة إلى العودة للشاشة السابقة بدلاً من الخروج المفاجئ من التطبيق.
- **ثبات الرابط (Same URL Invariant):** تتم إدارة التنقل عبر كائنات الحالة (`history.state`) مع الاحتفاظ بنفس الرابط دون تعديل المسار أو استخدام الوسوم (`#hash`)، لحماية استضافة Cloudflare Pages وتوجيهات 308 وعمل Service Worker.
- **منع تضخم سجل التاريخ:** إعادة تصيير نفس الشاشة ببيانات متطابقة لا تُنشئ إدخالاً جديداً في التاريخ (`isSameView`).
- **اتساق أزرار الرجوع داخل التطبيق:** تستدعي أزرار الرجوع دالة `goBack()` التي ترجع خطوة في تاريخ المتصفح (`history.back()`) عندما يكون عمق التاريخ أكبر من الصفر، لمنع التكرار أو الحلقات اللانهائية، مع الاحتفاظ بسلوك الخروج الافتراضي للنظام عند الوصول للشاشة الرئيسية (العمق 0).

### 💾 التخزين الدائم وتذكير النسخ الاحتياطي (Persistent Storage & Backup Reminder)
- **طلب حماية التخزين الدائم:** يطلب التطبيق حماية التخزين من الحذف التلقائي للمتصفح عبر `navigator.storage.persist()` مرة واحدة في الجلسة بمجرد وجود أي تقدم محفوظ. وبما أن هذه الميزة هي طلب اختياري للمتصفح وليست ضماناً مطلقاً (خاصة في متصفح Safari عندما لا يكون التطبيق مثبتاً كـ PWA)، تُعرض حالة الحماية بشفافية في شاشة الإحصائيات.
- **تتبع تاريخ النسخ الاحتياطي اليدوي:** يتم حفظ تاريخ آخر تصدير يدوي ناجح في `localStorage` (`deutsch_last_backup_v1`)، ويظل هذا التاريخ محفوظاً حتى عند تصفير التقدم، ولا يُدرج داخل ملفات النسخ الاحتياطي لتفادي تشويه التواريخ عند النقل بين الأجهزة.
- **شريط تذكير دوري:** إذا كان لدى المستخدم تقدم محفوظ (`stats.totalAnswered > 0`) ومضى أكثر من 14 يوماً على آخر تصدير (أو لم يقم بالتصدير مطلقاً)، يظهر شريط تنبيه لطيف في شاشة الإحصائيات فقط (وليس أثناء التمارين مطلقاً)، وهو قابل للإغلاق المؤقت لمدة 7 أيام.

- عند توفر إصدار جديد من Service Worker وتوليه التحكم في وجود نسخة سابقة مسيطرة على الصفحة (أو عند تحديثه لاحقاً في الجلسة نفسها بعد أول تثبيت)، يظهر شريط تنبيه دائم وقابل للإغلاق يحتوي على زر "تحديث الآن".

### 🌐 إتاحة النصوص الألمانية والتحسينات النصية (Accessibility & Text Improvements)
- **دعم قارئات الشاشة:** تمت إضافة سمات `lang="de"` و `dir="ltr"` لجميع عناصر وقوالب عرض الكلمات والجمل الألمانية وأدوات التعريف، لضمان قراءتها بالنطق الألماني الصحيح عبر قارئات الشاشة.
- **تصحيح العناوين الفرعية:** تم إزالة فئة التنسيق الألمانية العرضية (`class="de"`) من النصوص العربية في العناوين الفرعية والبطاقات واستبدالها بالفئة المناسبة (`class="cat-sub"`).
- **رسالة عدم تفعيل جافاسكربت:** تمت إضافة وسم `<noscript>` باللغة العربية الفصحى للتنبيه بضرورة تفعيل JavaScript.
- **وصف المزامنة غير المهيأة:** تم استبدال الشرح التقني لصندوق المزامنة غير المهيأ بجملة مبسطة ومناسبة للمتعلم توضح حفظ التقدم محلياً وإمكانية نقله بالتصدير والاستيراد.
